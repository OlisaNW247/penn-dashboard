## 1. Gradescope precedent: login capture, cookie storage, fetch/parse, sync, connected/expired state, onboarding

### Takeaway
Gradescope is a cookie-replay scraper. A visible WKWebView login pane (own persistent data store) captures cookies into a per-service Keychain item; a URLSession client replays them by hand in a `Cookie` header, scrapes HTML (no API), and `AppState.syncGradescope` reconciles the result into the SwiftData ledger as `source: .gradescope`. "Connected" is one persisted bool; "needs reconnect" is a separate two-sighting verdict, and as of 2026-10-27 the 24-hour cookie clock no longer applies to Gradescope.

**Ledger columns Gradescope uses**

### Inferences
- A new cookie-scraped source would copy: a `Service` case + Keychain item, a `LoginDataStores` entry with a fresh fixed UUID, a login pane + observer marker, a client with hand-built `Cookie` header + `CredentialOrigin` check, and a reauth rule that only believes a login form. The Gradescope design deliberately never disconnects on a failure; that is the pattern the codebase converged on after earlier lock-out bugs.
- Gradescope's "submitted" signal is scraped text; a courseware source with a JSON API would not need `GradescopeHTMLParser`-style keyword scanning or the title-blanking defenses.

### Gaps
- CLAUDE.md's Known-gaps bullet still says "Gradescope disconnects itself for good after 24 hours without a successful sync" and the `syncGradescope` comment at ~AppState.swift:4590 still describes the 24-hour drop; the code (SessionCookieStore.swift:408-412, AutoSyncCoordinator.swift:37-56) says that clock was removed 2026-10-27. Treat the code as current. Not verified on a device (CLAUDE.md says the 2026-10-27 hardening has not run on a phone).
- I did not read `GradescopeOverlay.swift` (grade-matching overlay used by the disabled Grade Watcher) in detail; it is irrelevant to a to-do-list source.

## 2. Ed Discussion precedent: hidden-WebView LTI launch from a Canvas course tool

### Takeaway
Ed is reached by (a) listing each Canvas course's nav tabs, (b) loading the Ed tool's Canvas `external_tools` launch URL (with `display=borderless`) in a hidden WKWebView that has had the Keychain's Canvas cookies injected, (c) reading Ed's `authToken` out of `localStorage` once the page lands on an `edstem.org` host, (d) calling Ed's JSON API with that token as `x-token`. The whole path is Penn-only, behind `FeatureFlags.edDiscussion`, never throws, and is an enrichment of the Canvas course-material sync. A Connect LTI tool in Canvas is the same shape of object (a `context_external_tool_<id>` tab with an `external_tools` URL), but the repo has no code that has launched anything except Ed.

### Cited Findings

**Finding the tool**
- `CanvasCourseContentClient.tabs(courseID:)` GETs `/api/v1/courses/:id/tabs?include[]=external&per_page=100`, all pages. The comment states it is the only endpoint that lists an LTI tool placed in course navigation but never linked from a module — [KIT/CanvasAPI/CanvasCourseContentClient.swift:93-107](LowHangingFruitKit/Sources/LowHangingFruitKit/CanvasAPI/CanvasCourseContentClient.swift).
- `CanvasCourseTab` fields: `id` (for an LTI tool `context_external_tool_<id>`), `label`, `type` ("external" for LTI), `html_url`, `url`, `hidden`, `visibility` — [KIT/CanvasAPI/CanvasCourseTab.swift:1-62](LowHangingFruitKit/Sources/LowHangingFruitKit/CanvasAPI/CanvasCourseTab.swift).
- `EdTabFinder.edTab(in:)` matches a tab whose `url`/`html_url` contains "edstem", else a tab whose label's first word starts with "ed". `EdTabFinder.launchURL(for:canvasBase:)` resolves the tab's `html_url` and appends `display=borderless`, because Canvas's normal `external_tools` page runs the tool in an iframe so the WebView's main frame would never leave Canvas — [KIT/Ed/EdDiscussionProbe.swift:29-87](LowHangingFruitKit/Sources/LowHangingFruitKit/Ed/EdDiscussionProbe.swift). Tests pin the tab JSON shape: [TESTS/EdDiscussionProbeTests.swift:59-95](LowHangingFruitKit/Tests/LowHangingFruitKitTests/EdDiscussionProbeTests.swift).
- `EdDiscussionCoordinator.findLaunchURLs` caches launch URLs per Canvas course id in defaults `edLaunchURLByCanvasCourseV1`, re-checks each course's tabs at most weekly (`edTabCheckedAtByCanvasCourseV1`, `tabRecheckInterval` 7 days), and records tab-request failures so they count as "unknown" not "no Ed" — [UI/EdDiscussionCoordinator.swift:68-82, 611-659](LowHangingFruitKit/Sources/LowHangingFruitUI/EdDiscussionCoordinator.swift).

**The launcher**
- `EdSessionLauncher` (@MainActor final class): builds a `WKWebViewConfiguration` with `websiteDataStore = LoginDataStores.canvas` (the same store the Canvas login pane uses), `customUserAgent = LoginUserAgent.mobileSafari`, never added to a view hierarchy — [UI/EdSessionLauncher.swift:46, 104-122](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift).
- Cookie injection: before loading, every cookie from `SessionCookieStore.load(service: .canvas)` is `setCookie`d into the Canvas data store, because a fresh hidden WebView otherwise bounces to Penn WebLogin (observed on a real phone 2026-10-09). Returns `.noCanvasSession` if the Keychain has none — [UI/EdSessionLauncher.swift:109-111, 134-148](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift). The comment rejects running `CanvasSessionRenewer` first because it could push Duo.
- Exactly one GET `webView.load` (a second load could re-launch the LTI tool), a 40 s hard timeout, and a settle wait: `EdLaunchNavigationDelegate` waits 3 s after the first `didFinish` on an Ed host, ignores `didFail*`, always allows navigation — [UI/EdSessionLauncher.swift:79-85, 150-163, 224-276](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift). `EdHosts.isEd` = host is edstem.org or a subdomain — [KIT/Ed/EdDiscussionProbe.swift:14-21](LowHangingFruitKit/Sources/LowHangingFruitKit/Ed/EdDiscussionProbe.swift).
- Token read: `readAuthToken` runs `localStorage.getItem("authToken") || localStorage.getItem("authToken:us")` through `callAsyncJavaScript` in the `.page` world, only while the WebView's host is Ed — [UI/EdSessionLauncher.swift:203-221](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift). Ed cookies (domain contains "edstem") are harvested as a fallback — [lines 173-182](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift). Outcomes: `landed`, `noEdSession`, `timedOut`, `throttled`, `noCanvasSession` (lines 63-79).
- Throttle: one launch in flight and at most one per 30 minutes unless `force` — [UI/EdSessionLauncher.swift:55-57, 85, 104-110](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift).
- Privacy posture in the file's header: the token and cookies leave only through `Outcome`; `EdSession.description` redacts the token; logs carry host and path only — [UI/EdSessionLauncher.swift:27-35, 63-72](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift).
- Why the probe was not reused: `EdDiscussionProbe` is `#if DEBUG`; the launcher duplicates its WebView code on purpose — [UI/EdSessionLauncher.swift:17-27](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionLauncher.swift).

**Token storage and client**
- `EdSessionTokenStore`: Keychain generic password, service `com.lhf.lowhangingfruit.session.ed.token`, this-device-only, explicitly non-synchronizable, inert under `swift test` (`SharedDefaults.isTestRunner`), deleted on Canvas disconnect — [UI/EdSessionTokenStore.swift:36-86](LowHangingFruitKit/Sources/LowHangingFruitUI/EdSessionTokenStore.swift). **Matching Ed courses to Canvas courses**

**Orchestration, flag, failure handling**
- `EdDiscussionCoordinator.sync` runs inside the course-material sync via `AppState.mergeEdDiscussion`, which returns immediately unless `FeatureFlags.edDiscussion` is true, the install is Penn (`canvasInstallation.id == CanvasInstallation.penn.id`), and it is not a test run — [UI/AppState+CourseKnowledge.swift:498-525](LowHangingFruitKit/Sources/LowHangingFruitUI/AppState+CourseKnowledge.swift). Called at lines 306 and 397 of the same file.
- Kill switch: `FeatureFlags.edDiscussion = true`; its doc says flipping it removes the launch, the fetch and the Settings row without touching the Canvas sync — [UI/FeatureFlags.swift:84-104](LowHangingFruitKit/Sources/LowHangingFruitUI/FeatureFlags.swift). Other readers: [UI/AppState+EdAnnouncementTasks.swift:286, 586](LowHangingFruitKit/Sources/LowHangingFruitUI/AppState+EdAnnouncementTasks.swift); [UI/SettingsPage.swift:639](LowHangingFruitKit/Sources/LowHangingFruitUI/SettingsPage.swift).
- Seven-step flow in `perform` (find tabs → reuse stored session or launch → `user()` → match → resolve targets → read/merge → status): [UI/EdDiscussionCoordinator.swift:155-354](LowHangingFruitKit/Sources/LowHangingFruitUI/EdDiscussionCoordinator.swift). A mid-run 401 ends the run and sets `edSessionDroppedV1` so the next sync's launch bypasses the throttle (lines 295-308).

## 3. Canvas side: does a Connect assignment already appear, and would its submitted state be detected?

### Takeaway

## 4. Ledger and model: `Assignment.Source`, the sourceID-prefix convention, and dedup against the Canvas copy

### Takeaway
`Assignment.Source` is a six-case String enum; the SwiftData row stores it as a free string and maps an unknown string to `.canvas`. The documented convention for adding a "new" source is to reuse an existing `Source` case (`.canvasAnnouncement`) and distinguish origin by a `sourceID` prefix (`ed-`, `syllabus-`) read by `AnnouncementOrigin`. Cross-source dedup (`AssignmentDeduplicator`) is hard-wired as exactly two sides, Canvas vs Gradescope, with a single `linkedID` field; announcement-derived rows use a separate dedup path.

### Cited Findings
- `Assignment.Source`: `canvas, gradescope, manual, canvasSuggestion, canvasModules, canvasAnnouncement` (raw-value strings) — [KIT/Models/Assignment.swift:7-38](LowHangingFruitKit/Sources/LowHangingFruitKit/Models/Assignment.swift). Identity is `"\(source.rawValue):\(sourceID)"` — line 52.
- Unknown-source fallback: `StoredAssignment.assignment` does `Assignment.Source(rawValue: sourceRaw) ?? .canvas` — [KIT/Persistence/StoredAssignment.swift:266-268](LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/StoredAssignment.swift). `decompose(id:)` returns nil for an unknown raw source — [same file:636-642](LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/StoredAssignment.swift). The ledger's `sourceRaw` is a plain `String` column — [same file:77](LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/StoredAssignment.swift).
- The explicit warning, in the code, not only CLAUDE.md: the comment above `edFindSourcePrefix` says there is "deliberately no new `Assignment.Source` and no new stored column": a new raw value would show a newer build's rows to an older build as Canvas calendar items (wrong source, and an id that no longer matches the stored id, so ticking one off would never stick); a new column is a SwiftData schema change, and an older build opening a newer store falls back to an empty in-memory ledger — [KIT/Canvas/AnnouncementLog.swift:343-358](LowHangingFruitKit/Sources/LowHangingFruitKit/Canvas/AnnouncementLog.swift).
- The prefix convention: `AnnouncementRecord.edFindSourcePrefix = "ed-"` with format `ed-{canvasCourseID}-{threadID}-{index}` (`edFindSourceID`, `edDocumentID(fromFindSourceID:)`), `syllabusFindSourceID(courseID:examKey:)` for `syllabus-{courseID}-{kind}[-n][-makeup]`; Canvas finds start with `announcement-` — [KIT/Canvas/AnnouncementLog.swift:360-440](LowHangingFruitKit/Sources/LowHangingFruitKit/Canvas/AnnouncementLog.swift). `AnnouncementOrigin` {canvas, ed, syllabus} and `Assignment.announcementOrigin` read the prefix, defaulting to `.canvas` for any other `.canvasAnnouncement` row — [same file:443-461](LowHangingFruitKit/Sources/LowHangingFruitKit/Canvas/AnnouncementLog.swift).
- What the origin drives downstream: `sourceLinks` label ("open in ed" vs "open in canvas") — [KIT/Models/SourceLink.swift:99-107](LowHangingFruitKit/Sources/LowHangingFruitKit/Models/SourceLink.swift); the store exempts all `.canvasAnnouncement` rows from aging (`isAgedOut`) — [KIT/Persistence/AssignmentStore.swift:805-845](LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/AssignmentStore.swift); the widget reader skips flagged announcement rows — [KIT/Widget/LedgerWidgetReader.swift:141, 182, 208](LowHangingFruitKit/Sources/LowHangingFruitKit/Widget/LedgerWidgetReader.swift).
- Why not just add a case: the `Source` doc comments explain `canvasModules` and `canvasAnnouncement` exist as separate cases specifically so `AssignmentStore.reconcile(_:source:)` (which partitions by source before flagging missing rows gone) never flags another sync's rows gone — [KIT/Models/Assignment.swift:12-37](LowHangingFruitKit/Sources/LowHangingFruitKit/Models/Assignment.swift). A prefix inside `.canvasAnnouncement` therefore shares that source's reconcile partition; the announcement code handles it by flagging gone separately (`reconcileAnnouncementPresence`, per CLAUDE.md).
- Schema machinery: the ledger is versioned (`LedgerSchemaV1`, `LedgerMigrationPlan` with empty `stages`), opened through one door `LedgerContainer.make`, which copies the store aside once before the first open at a newer schema, and which the widget (not allowed to migrate) refuses on an older recorded version — [KIT/Persistence/LedgerSchema.swift:18-60, 60-140](LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/LedgerSchema.swift). So a new column is now a migration with a backup, not a silent wipe, but no V2 has ever shipped (stages are empty) and the in-memory fallback on a failed open remains (comment, lines 3-15; CLAUDE.md "Known gaps": the `LedgerSchemaV1` migration has never opened a real pre-existing store).
- Per-service columns exist for the two services: `canvasSubmitted`/`canvasSubmissionObservedAt` and `gradescopeSubmitted`/`gradescopeSubmissionObservedAt`, and `StoredAssignment.assignment` only reads `gradescopeSubmitted` for `.gradescope` rows (`submitted: source == .gradescope ? gradescopeSubmitted : false`) — [KIT/Persistence/StoredAssignment.swift:138-157, 267-289, 398-402](LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/StoredAssignment.swift). All eleven non-optional-without-default properties listed at lines 56-62 are the CloudKit-eligibility blockers; any new property must be optional or defaulted.
- Dedup (Canvas vs Gradescope): `AssignmentDeduplicator.matchPairs(canvasItems:gradescopeItems:confirmedPairings:)` — same course (normalized code), exact normalized title within a 21-day gap, or Jaccard ≥ 0.6 titles with both dues within 26 h, greedy 1:1 — [KIT/Models/AssignmentDeduplicator.swift:1-30, 36-70, 372-460](LowHangingFruitKit/Sources/LowHangingFruitKit/Models/AssignmentDeduplicator.swift). `Match` has exactly `canvasID` and `gradescopeID` — line 29-36. `merge`/`mergedAssignment` keep the Canvas item's source, sourceID, title, due, url and set `submitted = canvas || gradescope` and `linkedID = gradescope.id` — [same file:480-560](LowHangingFruitKit/Sources/LowHangingFruitKit/Models/AssignmentDeduplicator.swift). Pairings persist on the ledger (`confirmedPairings`, `recordPairings`) — [KIT/Persistence/AssignmentStore.swift:1309-1350](LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/AssignmentStore.swift). Wiring: [UI/AppState.swift:7690-7700](LowHangingFruitKit/Sources/LowHangingFruitUI/AppState.swift).
- Other collapse paths in the same file: Canvas ICS vs Canvas Modules (`collapseCanvasDuplicates`, hides the module row; skipped when both Canvas ids are known and differ) lines 563-725; section overrides (`collapseCanvasOverrides`) 731-855; announcement twins (`isLikelyAnnouncementDuplicate`) line 132.
- The announcement/exam path is a separate dedup (`resolvingAnnouncementDuplicates`, `filteringAnnouncementDuplicates`), with its own survivor order (not hidden by rule, then dated, then Canvas, then id) — described in CLAUDE.md and wired at [UI/AppState.swift:7655-7686](LowHangingFruitKit/Sources/LowHangingFruitUI/AppState.swift).
- Completion carry: a swipe on the merged card completes both ids via `linkedID` (`isCompleted` line 8223-8224; `markCompleted`/`markActive` propagate to `linkedID`); a `linkedID` can hold one id only.

### Inferences
- A McGraw Hill row that is the same assignment as a Canvas LTI assignment (the likely case) is a third source in a place where the code assumes two. Options present in the code: (a) a distinct `Source` case (breaks old-build round trips by the rule above), (b) a new `sourceID` prefix inside an existing source (the documented route), or (c) enrich the Canvas row instead of adding rows (fits "Canvas is the display anchor" in `mergedAssignment`, but needs a field for the McGraw Hill submitted/score state; the one existing home is `scoreEarned`/`scoreMax`/`submitted` on the value type, plus per-source columns on the stored row).
- If rows are added with a prefix, `Match` and `linkedID` (`gradescope:`-prefix parsing in `SourceLink.linkedGradescopeURL`) are Gradescope-only; a third pairing needs either a generalized `Match` or a separate pass like the announcement dedup.

### Gaps
- I did not trace every consumer of `linkedID` (it is read in `isCompleted`, `markCompleted/markActive`, `SourceLink`, device sync at AppState+DeviceSync.swift:398-413, and `AssignmentStore.confirmedPairings`); a full list would be needed before adding a second twin per card.
- No evidence in the repo that an older build tolerates a newer build's `sourceID` prefix other than the doc comment's own claim; the prefix scheme has shipped for Ed finds (3.2.0 era), but there is no recorded downgrade test.

## 6. Size estimate of a Gradescope-style integration (counted from the repo)

### Takeaway
Gradescope proper is small in dedicated files (3 Swift source files, 1,571 lines) but its footprint is wide: 55 Swift source files mention it (28 with real code references), 65 test files mention it, and 5 Gradescope-named test files hold 144 `@Test` functions in 2,701 lines. Ed is the larger precedent (about 4,000 lines of dedicated source; 9 Ed-named test files, 173 `@Test`, 3,388 lines).

### Cited Findings
- Gradescope-named Swift source: `GradescopeClient.swift` 1,084 lines (client + `GradescopeHTMLParser` + term logic), `GradescopeReauthRule.swift` 129, `Grades/GradescopeOverlay.swift` 358 (grade-matching overlay for the disabled Grade Watcher; not needed by a to-do source). `git ls-files` shows exactly these three Swift source files with "gradescope" in the name. — [KIT/Gradescope/](LowHangingFruitKit/Sources/LowHangingFruitKit/Gradescope/), [KIT/Grades/GradescopeOverlay.swift](LowHangingFruitKit/Sources/LowHangingFruitKit/Grades/GradescopeOverlay.swift).

- Files that mention Gradescope: 21 in `KIT`, 34 in `UI` (55 total), of which 28 contain non-comment code references (`grep -rlE '[.]gradescope\b|Gradescope\w*\(|gradescopeItems|isGradescopeConnected|Service\.gradescope'`), and 65 of 257 test files contain `@Test` and "gradescope" (case-insensitive); 66 test files mention it at all.
- Gradescope-named tests: `GradescopeTests` 48 `@Test` (1,109 lines: parser/client), `GradescopeSessionKeepTests` 46 (730: reauth rule, empty-set outcome, wiring), `GradescopeTitleStatusTests` 21 (332), `GradescopeOverlayTests` 24 (405), `GradescopeTermStampTests` 5 (125) — total 144 `@Test`, 2,701 lines. Parameterized tests expand to more cases. Project total is 3,399 tests (CLAUDE.md Test baseline), so these are about 4%. Tests that exercise the wiring are spread over dozens of other files (e.g. `SessionCookieStoreTests`, `ReconnectCoverTests`, `AssignmentDeduplicator*Tests`, `SourceLinkTests`, `LoudAlertTests`).
- Chrome extension (optional, Penn): `src/adapters/gradescope.js` 51 lines, `src/core/gradescope.js` 746, `test/gradescope.test.js` 457 lines, 26 fixtures, plus `dedup.js` shared with Canvas; extension suite is 500 tests (separate gate).
- Ed (bigger precedent): `KIT/Ed/` 9 files = 1,823 lines; `UI/EdDiscussionCoordinator.swift` 699, `EdSessionLauncher.swift` 276, `EdSessionTokenStore.swift` 86, `EdDiscussionProbe.swift` 435 (DEBUG), `AppState+EdAnnouncementTasks.swift` 600; 9 Ed-named test files, 3,388 lines, 173 `@Test` (counted with `grep -c '@Test'`; the tests wc total came from `wc -l`).
- Backend footprint if the data touches the server: Ed needed a SQL migration (`20261002090000_ed_kind.sql`), a `DocumentKind` addition in `backend/supabase/functions/_shared/manifest.ts`, `backend/PROTOCOL.md`, and a `sync` redeploy needing the owner's go (CLAUDE.md "The backend", ED section). Gradescope needs none of this (on-device only).

### Inferences
- Order-of-magnitude: a Gradescope-shaped on-device integration is on the order of 1,500 to 2,500 lines of new Swift (client + parser, session store/pane, reauth/state, coordinator hooks, settings/onboarding rows) plus 100 to 200 tests, and edits to roughly 25 to 30 existing files. This is my extrapolation from the counts above, not a figure from the repo.
- An Ed-shaped one (LTI launch + session capture + coordinator + matcher + server kind) is nearer 3,500 to 5,000 lines of source and 150+ tests, plus a backend deploy.
- The heaviest cost in both precedents has been the long tail (reauth semantics, throttles, restore/drop, privacy copy), not the happy path; the Gradescope reauth rule alone (129 lines) has 46 tests.

### Gaps
- Test counts are `@Test` occurrences, not run results; parameterized tests are undercounted. No Swift toolchain here, so nothing was compiled or run.
- I did not measure the commit history cost (git log) of building Gradescope or Ed; the line counts are current-state only.

### Inferences
- The sharpest design decision the code forces is source identity: separate `Source` case (clean reconcile partition, breaks older builds' round trip) versus a prefix inside an existing case (documented as the safe route, but shares `.canvasAnnouncement`'s reconcile and aging exemptions) versus enriching the Canvas row. The repo records the owner's preference for the prefix route ("There is deliberately no new `Assignment.Source`…").
- The cheapest first experiment is Tier 0 (observe whether a real Penn Connect assignment already reaches the dashboard and ever reads done), because it needs no code and the repo shows no instrumentation that would already tell. A `submissionDiagnosticLines` DEBUG helper exists per CLAUDE.md ("Read the session state first … `submissionDiagnosticLines` on a DEBUG build") and could be used for it.

### Gaps
- No existing seam for "a source with its own pooled-on-server rows and its own ledger source" (Ed produces documents and `.canvasAnnouncement` rows; Gradescope produces ledger rows only). A new source that needs both would combine two mechanisms that have never been combined.
- Process constraints from CLAUDE.md that affect any plan but are not code seams: new Swift must be compiled on a Mac before it counts; backend deploys need Olisa's go; PRIVACY.md and the posture sentence change in the same commit; Marco has said not to touch the course-material sync; there is no Swift toolchain in the cloud container.
