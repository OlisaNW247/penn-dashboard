# Signed out of Canvas with the cookies still saved (2026-11-01)

Read-only investigation of Marco's iPhone 17 Pro on 2026-11-01, against
the shipped 3.4.0 (17) source (`release/3.4.0`, in `origin/v8`; `v8` has
not touched the sign-in files since). No app code changed. The phone now
runs the Debug 3.4.0 (17) build from
`.claude/worktrees/release-3.4.0/build/DerivedData` installed over the
App Store copy, so its App Group plist and renewal log are readable
(same data, same Keychain).

## What the phone said

Read off the App Group plist as the store build left it, then from
`-LHFSessionDiagnostics` on the Debug build (all times UTC; the phone is
on EST, UTC-5):

| Fact | Value |
|---|---|
| `canvasSessionConfirmedDeadV1` | false |
| `autoLoginAwaitingDuoV1` | false |
| `autoLoginDisabledReasonV1` | absent (password never rejected) |
| `stayLoggedInEnabledV1`, PennKey password on file | true, true |
| `lastSilentRenewalSummaryV1` | `landedOnLoginPage · 12:25 · background` |
| `lastSilentRenewalAttemptAtV1` | 17:25:25Z (12:25 local) |
| `lastSilentRenewalAttemptOutcomeV1` | **absent** (see below) |
| `lastCredentialSubmissionAtV1` | absent: no attempt has ever submitted the saved password |
| `canvas_session` captured | 18:15:20Z, the second the app was launched from the Mac |
| `_gid` captured (previous harvest) | 2026-10-31 04:55Z |
| Crash reports | none since 2026-10-26; the five on file are the notification-tap crash in builds 12 to 14, already fixed |

The 18:15:20Z capture was not a login and not a renewal (the renewal
summary did not move). It is the Grade Watcher's cookie-rotation merge
(`GradeWatcherStore.swift:256`): the launch-time grade fetch sent the
folded cookie jar (persisted set plus the live `WKWebsiteDataStore`
cookies, live winning: `AutoSyncCoordinator.canvasCookies`), Canvas
answered with a fresh `Set-Cookie: canvas_session`, and the store saved
it with a new `capturedAt`. **Canvas accepted the session at 13:15.**
The login was never dead.

## The sequence that produced the banner

1. The last real harvest was around 2026-10-31 00:55 local. The 24-hour
   rule in `SessionCookieStore.load` (`isStale`, 24 h for Canvas) therefore
   declared the saved `canvas_session` stale from about 2026-11-01 00:55.
   From then on `isExpired` read true, so `canvasSessionExpired` was true
   on every `AppState` built, and so was the banner condition, unless a
   silent renewal was in flight.
2. At 12:25 local a **background wake** (they run again since the
   hardening work; `LHFBackgroundRefresh.run` marks its state
   `.background`) built an `AppState`, saw the cookie expired, and ran
   `CanvasSessionRenewer` under the 20-second `backgroundTimeout`. It ended
   as `landedOnLoginPage`. Two ways that happens while the session is in
   fact alive: the hidden WebView had not finished the hop inside 20 s
   while parked on a login host (`timeoutOutcome` returns
   `.landedOnLoginPage`, not `.timedOut`), or the WebView store needed the
   IdP round trip and Penn's IdP page was still loading. Either way it was
   recorded as a real attempt at 12:25.
3. That timestamp is persisted and seeds every later renewer's one-hour
   cooldown (`CanvasSessionRenewer.init`, `lastAttemptAt`; added so two
   quick relaunches could not latch the session dead). So when Marco
   opened the app between 12:25 and 13:25, `refreshCanvasSessionExpiredState`
   flipped `canvasSessionExpired` true and called the renewer, which
   answered `.notAttempted("within the 1h cooldown")` at once.
   `isSilentRenewalInFlight` never became true, so `ContentView` showed
   the "needs a refresh" banner immediately, over a saved, working cookie
   set. `retrySilentRenewalIfDue` could not help: the last outcome was a
   landing, so it also waits for the full hour (`shouldRetrySilentRenewal`);
   only a `.timedOut` outcome gets the 10-minute retry.
4. At 13:15 the launch from the Mac ran the grade refresh, Canvas accepted
   the folded cookies, the rotation re-stamped `canvas_session`, the
   recompute read `isExpired` false, and the banner went away on its own.
   This is the "sometimes clears by itself" behaviour already listed in
   CLAUDE.md's Known gaps, now explained.

Why `lastSilentRenewalAttemptOutcomeV1` is absent while the summary and
timestamp are present is unexplained; `recordSilentRenewal` writes all
three together. It is worth a look while fixing, because
`shouldRetrySilentRenewal` reads that key on the next launch.

## Root cause, in one sentence

The app decides "signed out" from a local clock (24 hours since the last
cookie save) and shows the student that verdict before anyone has asked
Canvas, and the one mechanism meant to correct it (the silent renewal) can
be locked out for an hour by a background attempt that never had a chance
to finish.

Three contributing design facts, each verified in the 3.4.0 source:

- **The clock is the verdict.** `SessionCookieStore.isExpired` →
  `canvasSessionExpired` → banner, with no server round trip in between.
  Canvas's own cookie lifetime is "1 day from the last request"
  (`config/initializers/session_store.rb`, `expire_after ||= 1.day`,
  re-issued on every authenticated response), and the Grade Watcher
  already re-stamps the saved cookie on every successful fetch, so for
  anyone who opens the app daily the 24-hour rule trips only when the app
  was closed for a day, which is exactly when the session is often still
  alive.
- **Background and foreground attempts share one cooldown slot**, and the
  background one is the weaker attempt (20 s, no latching, no retry
  shortening) yet it blocks the strong one.
- **A timeout parked on a login host is recorded as a landing**, which
  denies it the 10-minute retry that a bare timeout gets.

## The fix: ask Canvas first, and never let the clock alone show a banner

Land on a branch off `origin/v8`; sign-in files there are identical to
3.4.0. Four parts, in order of value. Each is small, pure-testable, and
can ship alone.

1. **Probe before declaring expired.** `CanvasSessionProbe.probe`
   (`GET /api/v1/users/self`, verdict `.alive` / `.dead` / `.unknown`)
   already exists and is used only by `GradeWatcherView`. In
   `refreshCanvasSessionExpiredState`, when the *only* reason for expiry is
   the clock (`isExpired` true, `confirmedDead` false, login not missing),
   run the probe with the folded cookie jar before setting
   `canvasSessionExpired`. `.alive`: merge the response's rotated cookies
   (re-stamp `capturedAt`), stay signed in, no renewal. `.dead`: proceed
   exactly as today. `.unknown` (offline): keep the previous value, show
   nothing new. The 24-hour rule becomes "time to re-check", which is what
   Olisa's restored rule was always doing well: starting a check on open.
   Because the fold already contains the live WebView cookies, this is the
   same request the grade fetch makes a moment later, so it costs one small
   GET and nothing else.
2. **Separate the cooldown slots.** Persist the last *foreground* attempt
   and the last *background* attempt separately; the foreground renewer's
   one-hour gate reads only foreground attempts (plus the global in-flight
   guard). A background wake may still run its 20-second attempt, but it
   can never deny the student's own open a real try.
3. **Record a background timeout as `.timedOut`.** In
   `CanvasSessionRenewer.performAttempt`, when `signal == .timedOut` in the
   background context, return `.timedOut` regardless of the parked host;
   keep today's host classification for the foreground 30-second attempt,
   where it is evidence. `.timedOut` already gets the 10-minute retry and
   never latches.
4. **Show the banner only after a real foreground verdict.** Make the
   banner condition "canvasSessionExpired AND (confirmedDead OR the last
   foreground attempt failed)". The clock alone, or a refused attempt,
   shows nothing; the student sees the banner only when Canvas or the IdP
   has actually said no. With part 1 in place this is mostly belt and
   braces, but it is what makes "never again" hold when the probe is
   `.unknown`.

Also worth doing in the same branch: a **keepalive on open**. Every
foreground open already fetches grades, which rotates the cookie; make the
re-stamp explicit by calling the probe (part 1) on every open when the
cookie is older than, say, 12 hours, so a daily user's `capturedAt` never
gets near 24 hours and the whole renewal path becomes the rare case it was
meant to be.

What this does not change: Olisa's 24-hour rule stays byte for byte in
`SessionCookieStore.load` (CLAUDE.md, the 24-hour trap); it just stops
being the last word. Nothing here touches sync or Ed. Duo remains a hard
boundary.

## How to prove it on the phone

The Debug 3.4.0 (17) build is on Marco's phone now, so the plist and
`debugRenewalLogV1` are readable (CLAUDE.md, Commands). For the fix:
install the branch's Debug build, launch with `-LHFAgeCanvasSession`, and
expect the renewal log to show the probe answering `alive` and no
`canvasSessionExpired false -> true` line. Then simulate the failing case
by letting a background wake run (or seeding `lastSilentRenewalAttemptAtV1`
to "now" with a background summary) and opening the app: expect a real
foreground attempt, not `within the 1h cooldown`. The runbook in
`docs/SIGNOUT_VERIFICATION.md` still applies for the two-phone check.
