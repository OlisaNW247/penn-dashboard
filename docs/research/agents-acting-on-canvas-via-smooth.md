# Agents can read Smooth, not borrow Canvas

An external agent (OpenAI's dots, Meta's Muse, Anthropic's Claude Duet, or an ordinary Claude/ChatGPT connector) can plausibly be given Smooth's assignment list, but it cannot be given Smooth's Canvas sign-in in any form that is safe, durable, or allowed, and the one thing that keeps Smooth signed in at Penn does not travel with the cookie anyway. Smooth stays signed in because a hidden WKWebView re-walks Penn's SAML chain with the IdP and Duo cookies kept in its own WebKit data store plus a saved PennKey password, and only while the app is in the foreground; the Keychain copy of the Canvas cookie that an export would hand over is a device-bound bearer credential that Smooth itself treats as dead 24 hours after its last save, so a cloud agent holding it would be signed out within a day and have no way back in short of the student typing PennKey and Duo into the agent's browser. No agent platform offers a developer-facing way to inject a session: cloud-VM agents (dots, Duet, Muse) hold their own browser and ask the human to take over at login walls, and the only place a student's Canvas session is already usable by an agent is the student's own signed-in Chrome profile via Claude in Chrome or the ChatGPT extension. Canvas's REST surface would let an authenticated client submit text, URL, file-upload, media and annotation assignments and start or complete Classic Quizzes, but not New Quizzes or LTI tools such as Gradescope, and at Penn the clean credential for that work, a scoped access token, is disabled for students by the institution, leaving only the cookie. Smooth today has no Canvas write path, no URL scheme, no App Intents, no local server, and a backend whose published first principle is that the server never talks to Canvas, so every "turn it in" design is new code. The realistic ranking is therefore inverted from the question's framing: the cheapest viable product is on-device App Intents and a read-only connector that lets any agent see what is due, the only defensible "act" design is a Mac companion that signs in to Canvas itself and executes a handful of typed, confirmed verbs behind a local MCP server, and cookie export, phone-as-proxy and a server that acts on Canvas should be rejected on iOS mechanics, Apple review, Instructure policy and Smooth's own privacy promises.

**How to read the evidence.** Each citation is tagged. *primary* means the researcher read the page, spec, or source file; *search summary* means only a search engine's model-written summary of the page was available (the page itself was often behind a 403 or JavaScript); *repo* means the claim comes from Smooth's own code or docs at `/Users/marcoopertti/penn-dashboard` on branch `codex/simplify-canvas-onboarding` (HEAD `56ccd01`, with uncommitted working-tree edits) as of 2026-10-30. Press coverage of dots, Duet and Muse is all *search summary*; no primary OpenAI, Anthropic or Meta announcement for those three products was read.

## Three cloud-VM agents launched in six weeks, and none takes a handed-over session

The three products named in the brief are real and recent, and their shared shape decides most of what follows. OpenAI's **dots** are always-on personal agents launched at DevDay on **2026-09-29**, each with its own cloud computer and browser, connecting to 4,000-plus apps and starting with Pro and Business Premium outside the EEA, Switzerland and UK ([TechCrunch](https://techcrunch.com/2026/09/29/openai-launches-dots-its-bubbly-agentic-avatar/), search summary; [AI Weekly](https://aiweekly.co/alerts/openai-launches-dots-always-on-chatgpt-agents-at-devday), search summary). Anthropic's **Claude Duet** entered research preview on **2026-10-21** for US Pro and Max on iOS, Android and web, running each user's work in a cloud VM with its own browser ([Let's Data Science](https://letsdatascience.com/news/anthropic-opens-claude-duet-research-preview-for-proactive-a-16522f5d), search summary; [HackerNoon](https://hackernoon.com/what-is-claude-duet-inside-anthropics-always-on-ai-assistant), search summary). Meta's **Muse** launched **2026-09-08** in the US on iOS, Android, muse.ai and WhatsApp, and is described as able to "open a browser, fill out forms, and negotiate" on "a dedicated, secure virtual machine" ([PBS NewsHour](https://www.pbs.org/newshour/nation/meta-launches-personal-ai-agent-muse-to-help-with-everyday-tasks), search summary). No product called "ChatGPT Dot" exists under that name; OpenAI's hardware device was still unreleased in mid-2026 reporting, so "dot" almost certainly means dots. The older OpenAI browser agents are gone: Operator was folded into agent mode and removed, agent mode now redirects to **ChatGPT Work** (announced 2026-07-09), and the Atlas browser stopped working on 2026-08-09, its agentic features moving into the ChatGPT desktop app, a Chrome sidebar extension and a remote cloud browser ([OpenAI help](https://help.openai.com/en/articles/11752874-chatgpt-agent), search summary, page returned 403; [PPC Land](https://ppc.land/openai-kills-atlas-browser-folds-it-into-new-chatgpt-work-agent/), search summary). Anything written about Operator or Atlas in 2025 describes a product that no longer runs.

What each can do in a browser matters less than how each gets signed in, and here every platform converges on the same answer: the human logs in, in a browser the vendor controls or can see, and the vendor keeps the resulting state. Duet "never directly sees your passwords or sign-in tokens", pays through a Stripe Link virtual card, auto-runs read and draft actions, requires approval for send, pay, sign and delete, and blocks securities trading and money movement even when approved; how a Duet VM gets past a login wall is not explained anywhere that was read ([HackerNoon](https://hackernoon.com/what-is-claude-duet-inside-anthropics-always-on-ai-assistant), search summary). The retired OpenAI agent mode paused screenshots and asked the user to "take over" the virtual browser when a site wanted credentials, and advised users to sign out and clear cookies afterwards because sessions persisted ([Carly](https://www.usecarly.com/blog/what-is-chatgpt-agent/), third-party guide, search summary). dots keep their cloud computer "separate from the user's computer unless the user connects them" ([AI Weekly](https://aiweekly.co/alerts/openai-launches-dots-always-on-chatgpt-agents-at-devday), search summary). Muse's login and approval behaviour is not described in any source found. The pattern among dedicated agent-browser vendors is identical: Browserbase Contexts persist a profile after a one-time manual login via Session Live View, warn that sites may still expire cookies or force logout on concurrent use, and expose no cookie-import method ([Browserbase Contexts](https://docs.browserbase.com/platform/browser/core-features/contexts), primary); Steel, Hyperbrowser and Anchor all snapshot cookies from a live vendor session and tell customers to treat the snapshot as a credential ([Steel](https://docs.steel.dev/overview/sessions-api/reusing-auth-context), search summary; [Anchor](https://docs.anchorbrowser.io/essentials/managed-authentication), search summary). The single vendor that imports state from outside its cloud is Browser Use, whose script uploads a *local Chrome's* login state and recommends refreshing any profile older than seven days because cookies expire ([Browser Use profile sync](https://docs.browser-use.com/cloud/guides/profile-sync.md), search summary). Nobody documents importing arbitrary cookies from a third-party app on a phone.

The exception that proves the rule is the agent running in the student's own browser. Claude in Chrome (Pro, Max, Team, Enterprise) acts "directly [on] websites on your behalf", defaults to auto-approve with pauses for consequential actions, and Anthropic's own safety page advises using "a separate browser profile without access to sensitive accounts" and letting 1Password handle sign-ins so passwords stay out of Claude's context ([Claude Help: getting started](https://support.anthropic.com/en/articles/12012173-getting-started-with-claude-for-chrome), primary; [Claude Help: safety](https://support.claude.com/en/articles/12902428), primary). Neither page says in so many words that it uses the signed-in profile, but the advice only makes sense if it does. OpenAI's Atlas agent mode, before retirement, had an explicit "logged-in" mode using the user's existing sessions and a "logged-out" mode that did not ([OpenAI Atlas agent mode](https://help.openai.com/en/articles/12628199-chatgpt-atlas-agent-mode), search summary), and ChatGPT Work's desktop app is reported to drive a built-in multi-tab browser that can "sign into accounts" ([Pasquale Pillitteri](https://pasqualepillitteri.it/en/news/7783/openai-shuts-down-atlas-agentic-features-move-to), search summary). This is the only surface where a Canvas session the student already holds is usable by an agent without anyone exporting anything, and it is a desktop surface: the Chrome extension runs on a Mac, not an iPhone.

For connecting an app rather than a browser, remote MCP is the common denominator. The current MCP authorization draft makes an MCP server an OAuth 2.1 resource server that **MUST** publish RFC 9728 Protected Resource Metadata, requires clients to send RFC 8707 `resource` indicators and PKCE, requires servers to validate token audience and "MUST NOT accept or transit any other tokens", prefers Client ID Metadata Documents, and deprecates Dynamic Client Registration ([MCP authorization, draft](https://modelcontextprotocol.io/specification/draft/basic/authorization), primary). Claude accepts custom remote connectors on every plan including Free (one connector), added under Customize → Connectors with a URL, with OAuth via Claude's published identity, automatic registration, or a developer's own client, and connections originate from Anthropic's cloud so the server must be publicly reachable ([Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), primary). ChatGPT exposes full MCP client access through developer mode on Pro, Plus, Business, Enterprise and Education, and general distribution goes through the plugin directory, where OpenAI tells servers to use OAuth 2.1 and "Require confirmation for consequential write actions", with `readOnlyHint` and `destructiveHint` annotations steering ChatGPT's confirmation behaviour ([OpenAI: build an MCP server](https://developers.openai.com/plugins/build/mcp-server), primary; [OpenAI developer mode](https://developers.openai.com/api/docs/guides/developer-mode/index.html), search summary, page 404). Whether Duet accepts custom MCP servers is unconfirmed, and consumer Muse reportedly has no custom-MCP setting while Muse Code does ([Parallel](https://parallel.ai/articles/meta-muse-custom-integrations), search summary). Local stdio MCP servers, the pattern every community Canvas server uses, fit Claude Desktop and Claude Code but not the phone apps or the cloud VMs.

## Canvas replays cookies and signs out daily, and Penn has shut the token door

The "sign in" half of the question turns on how Canvas authenticates and how long it keeps a session. The source answers are more permissive than the brief assumed and less convenient than the agent would need. Canvas authenticates each request by JWT first, then access token (Bearer header or `access_token` parameter), then the Rails encrypted-cookie session, and it attempts cookie auth for any request a token did not authenticate, with no `/api` carve-out in the file read ([authentication_methods.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/authentication_methods.rb), primary via summarised fetch). The session cookie's source key is `_normandy_session` with `expire_after` defaulting to **`1.day`**, overridable at runtime from Consul; the remember-me path lasts two weeks as a *single-use* `SessionPersistenceToken` that is consumed and replaced on each use ([session_store.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/config/initializers/session_store.rb), primary; [pseudonym_session.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/models/pseudonym_session.rb), primary). None of the three files read (`pseudonym_session.rb`, `authlogic_mods.rb`, `authentication_methods.rb`) binds the session to an IP or user agent; a session is invalidated if it predates the user's `last_logged_out`, if a CAS or OIDC upstream token expired, or if the pseudonym is suspended ([authentication_methods.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/authentication_methods.rb), primary). Two consequences follow, both inferences rather than tested facts. A Canvas cookie replayed from another IP would probably work until it expires, though a WAF or Instructure cloud layer could add checks the source does not show, so this needs an empirical test before anyone builds on it. And a student who logs out in any browser kills every copy at once through `last_logged_out`. The `SessionsTimeout` module that implements idle-vs-absolute semantics could not be located, community figures for the institutional idle timeout disagree (24 versus 48 hours), and Penn's actual value is unpublished ([Illinois](https://answers.uillinois.edu/112599), search summary; [community thread](https://community.canvaslms.com/t5/Archived-Questions/Canvas-session-timeout-setting/m-p/148249), search summary). Smooth's own "24 hours since last save" rule happens to match the `1.day` default, which is the strongest available hint about what Penn runs.

Writes need CSRF. `verified_request?` passes when the method is GET or HEAD, when the request is an API request that is not `in_app`, or when the token from the form parameter or `X-CSRF-Token` header validates against the cookie-held secret via `CanvasBreachMitigation::MaskingSecrets`; `protect_from_forgery with: :exception` is on and a blank `_csrf_token` cookie redirects to login with `needs_cookies=1` ([request_forgery_protection.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/canvas/request_forgery_protection.rb), primary; [application_controller.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/app/controllers/application_controller.rb), primary). The definition of `in_app?` was not found; the reading consistent with the Canvas web UI working is that cookie-authenticated API calls are "in app" and so carry CSRF, which is what Canvas's own JavaScript does. A cookie client therefore GETs any page, reads `_csrf_token`, and sends it as `X-CSRF-Token` on POSTs. Smooth has exactly one piece of code that does this, the gated-off access-token minter, which runs a `fetch` inside an already-signed-in WKWebView page rather than from URLSession (`LowHangingFruitKit/Sources/LowHangingFruitUI/CanvasAccessTokenMinter.swift`, repo).

The clean credential for an agent would be a token, and Penn has removed it. Canvas account admins can "Restrict students from creating personal access tokens", extended to observers in November 2025 ([Deploy Notes 2025-11-05](https://community.canvaslms.com/t5/Canvas-Releases/Canvas-Deploy-Notes-2025-11-05/ta-p/661038), search summary), and Olisa's own Penn settings page shows "+ New Access Token" disabled with the tooltip "Your Canvas administrators have chosen to limit your ability to generate your own access token" (`CLAUDE.md`, repo). Smooth already contains a complete mint-at-login, Keychain-store and Bearer-use path for 120-day tokens, switched off by `FeatureFlags.canvasAccessTokens = false` because every mint would 403 at Penn (`LowHangingFruitKit/Sources/LowHangingFruitUI/FeatureFlags.swift`, repo). The alternative, OAuth2, requires an institution-issued developer key; Canvas's docs say manual tokens are for testing only, that asking other users to paste a token violates the API policy, and that multi-user applications must use OAuth, with one-hour access tokens and refresh tokens for keys issued after October 2015 ([Canvas OAuth2](https://canvas.instructure.com/doc/api/file.oauth.html), primary). Several universities justify the restriction by saying user tokens "circumvent multi-factor authentication and university SSO" and that AI agents can overload the API ([UNH/PSU KB](https://td.usnh.edu/TDClient/60/Portal/KB/Article/5520/Canvas-User-API-Token-Access-UNH-PSU), search summary). Every community Canvas MCP server found (plyght, admin978, mandaza, vishalsachdev and others) takes `CANVAS_BASE_URL` plus a personal access token ([LobeHub](https://lobehub.com/mcp/plyght-canvas-mcp), primary listing; [admin978/canvas-mcp](https://github.com/admin978/canvas-mcp), primary), so the entire community pattern fails for Penn students, and no official Instructure MCP server for outside agents was found ([Carly](https://www.usecarly.com/blog/claude-canvas-lms-integration/), vendor blog, unverified).

If a client does hold a valid credential, the Submissions API covers most but not all assignment types. `POST /api/v1/courses/:course_id/assignments/:assignment_id/submissions` requires an actively enrolled student and a `submission[submission_type]` among the assignment's allowed types: `online_text_entry` (body), `online_url`, `online_upload` (`file_ids[]`), `media_recording`, `basic_lti_launch`, and `student_annotation`; there is no API to list user files, none to create media comments, and Google Docs submissions are unsupported ([Submissions API](https://canvas.instructure.com/doc/api/submissions.html), primary). File upload is a three-step flow, metadata POST to `.../submissions/self/files`, multipart POST to the returned `upload_url` within 30 minutes, then confirmation, and the documentation shows only Bearer examples, so whether that endpoint accepts cookie plus CSRF is untested ([File Uploads](https://canvas.instructure.com/doc/api/file.file_uploads.html), primary). Classic Quizzes have start and complete endpoints (the latter needing `attempt` and `validation_token`) with the answer endpoint in a separate reference not read ([Quiz Submissions API](https://canvas.instructure.com/doc/api/quiz_submissions.html), primary). New Quizzes expose no student-response endpoint according to community threads, and LTI external-tool assignments, which is what every Gradescope-linked assignment is, are completed inside the tool's own session, so a Canvas client cannot finish them at all ([community idea](https://community.canvaslms.com/t5/Canvas-Ideas/API-Student-Responses-to-Questions-in-New-Quizzes-and-Grades/idi-p/614516), search summary). Reading state is straightforward: `workflow_state` (`submitted`, `unsubmitted`, `graded`, `pending_review`), `submitted_at`, `missing`, `late`, and bulk `students/submissions` with `include[]` options ([Submissions API](https://canvas.instructure.com/doc/api/submissions.html), primary).

| Assignment type | Programmatic submission | Source confidence |
|---|---|---|
| Text entry, URL, file upload, media recording, student annotation | Yes, one `POST .../submissions` (file upload is three steps) | primary (Canvas API docs) |
| Classic Quiz | Start and complete endpoints exist; answer-posting endpoint not read | primary for start/complete |
| Discussion assignment | Via Discussion Topics API, not fetched | unverified |
| New Quiz | No student-response endpoint found | search summary (community) |
| External tool / LTI, including Gradescope | No; completed in the tool's own session | inference from absence in docs |

The last layer is Duo. Duo's remembered-device trust is a browser cookie, typically **30 days**, that works only in the browser that set it and resets when cookies are cleared ([Dartmouth KB](https://services.dartmouth.edu/TDClient/1806/Portal/KB/Article/64944/Undo-Duo-s-Remember-me-for-30-Days-Setting), search summary; [Berkeley](https://calnet.berkeley.edu/news/new-changes-duo-browser-workflow), search summary). Smooth's device evidence agrees: a renewal on 2026-09-27 re-issued Duo's 30-day `browsertrust` cookie (`CLAUDE.md`, repo). Nothing read indicates the trust is portable, and whether Duo also binds it to user agent or IP is unknown. A cloud agent given the Canvas cookie alone gets no Duo trust and no IdP session; when the day-old cookie dies, the agent's next move is a PennKey password field followed by a Duo push the student must answer on their phone, in the agent's browser, with no Smooth code in the loop.

## Smooth's session is foreground, daily, Penn-only and read-only, and its backend never talks to Canvas

Everything an integration could draw on sits in a few files, and reading them deflates the premise that "Smooth is signed in" is a transferable asset. Canvas and Gradescope cookies are one JSON blob per service in the Keychain under `com.lhf.lowhangingfruit.session.<canvas|gradescope>`, stored with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and no `kSecAttrAccessGroup`, so they never sync, never migrate, and are unreadable even by Smooth's own widget extension, whose entitlements carry only the App Group (`LowHangingFruitKit/Sources/LowHangingFruitUI/SessionCookieStore.swift` lines 29-32 and 300; `App/LHFApp.entitlements`, repo). Apple's documentation confirms that ThisDeviceOnly items do not migrate and cannot be marked synchronizable ([kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly), primary; [kSecAttrSynchronizable](https://developer.apple.com/documentation/security/ksecattrsynchronizable), primary), and Keychain sharing works only among apps from the same developer team ([Apple: sharing keychain items](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps), primary), so no agent app from OpenAI, Meta or Anthropic could ever read them in place. Replay is explicit: `CanvasAuth.apply` writes a `Cookie` header and the clients set `httpShouldHandleCookies = false` (`LowHangingFruitKit/Sources/LowHangingFruitKit/Canvas/CanvasAccessToken.swift` lines 371-379, repo).

The 24-hour rule is Smooth's clock, not Canvas's. In `load(service:)`, a cookie with a real `expiresDate` survives while that date is ahead; a cookie with none survives while `now - capturedAt < 24h`, and `capturedAt` is rewritten on every save, so it measures time since the last harvest, not since login (`SessionCookieStore.swift` lines 59-70, 113-130, repo). `isExpired` is "something is persisted and `load` returns nothing", and that flag flipping drives both the "needs a refresh" banner and the silent renewal (`SessionCookieStore.swift` lines 204-206; `AppState.swift` around line 1794, repo). The renewer itself is a hidden `WKWebView` that loads the Canvas root inside a persistent per-service `WKWebsiteDataStore(forIdentifier:)`, walks Penn's SAML chain using the IdP and Duo cookies that live in that WebKit store rather than in the Keychain, and if needed submits the saved PennKey password exactly once; it has a one-hour attempt cooldown, a six-hour password cooldown and a 30-second hard cap, and its gate has no foreground check only because every background wake crashes before reaching it (`LowHangingFruitUI/CanvasSessionRenewer.swift`; `LoginDataStores.swift` lines 38-50; `BackgroundRefresh.swift` lines 47-56, repo). This is the point the brief's framing misses: **the capability to stay signed in is the WebKit data store plus the password, not the Canvas cookie.** Export the cookie and you export a day; the thing that makes a new day is non-exportable by construction. The feature is also Penn-only, because `PennKeyCredentialsSheet` is gated on `CanvasInstallation.penn`, and it has been verified hands-free on two phones in the foreground (8 seconds on 2026-09-27) and never once in the background (`CLAUDE.md`, repo). The live App Store build, 3.0.0 (11), is further weakened by an analytics-cookie hole in which `_ga` and `last_known_canvas_host` keep `load` from ever returning empty, so the rule never trips; a fix (`gatedOnLiveSession`, keyed on `canvas_session` and `_normandy_session` names) exists only in the uncommitted working tree and has not been compiled or run by anyone in this research (`SessionCookieStore.swift` working tree lines 141-179, repo).

What Smooth knows is rich enough for an agent to act on. Each `StoredAssignment` row carries `canvasSubmitted` and `gradescopeSubmitted` with observation timestamps, a student-owned `userCompleted` tick, scores, the Canvas URL and the assignment id parsed from the ICS event's URL fragment (`LowHangingFruitKit/Sources/LowHangingFruitKit/Persistence/StoredAssignment.swift` lines 74-200, repo). Submission truth comes from `CanvasGradesClient` GETting `assignment_groups?include[]=assignments&include[]=submission` with the cookie, on a 15-minute throttle inside a 5-minute foreground loop, treating a 401 or an HTML 200 as `sessionExpired` (`Canvas/CanvasGradesClient.swift` lines 107-185; `AutoSyncCoordinator.swift`, repo). It is a point-in-time poll that goes stale with the session. And it is strictly read-only: a grep over the Swift sources finds `POST` or `DELETE` only toward Supabase, the announcement extractor and the gated token minter; nothing submits, posts or edits on Canvas (repo). Smooth has no Canvas CSRF-handling URLSession code, so "turn it in" is a new subsystem, not a flag flip.

The inbound surface is empty. No `CFBundleURLTypes`, no `AppIntent`, no `NSUserActivity`, no share extension, no `NWListener`; the only cross-process channels are the widget's App Group `widget-snapshot.json` and the opt-in, default-off CloudKit ledger mirror, and Siri/Shortcuts is a roadmap line (`project.yml`; `ROADMAP.md` lines 105-107, repo). The backend is a Supabase project with anonymous GoTrue accounts and eight Edge Functions whose contract opens with the principles that "Canvas credentials never reach the server… The server never talks to Canvas" and that it receives "Never grades, completions, submission state, the work list, the student's name, or transcripts of questions", with enrollment client-asserted because verifying it would need server-held credentials (`backend/PROTOCOL.md` lines 7-24 and 714-722, repo). The student-facing `docs/PRIVACY.md` promises that cookies and the feed URL stay in the Keychain this-device-only and that the PennKey password only ever goes to Penn's login page, and `CLAUDE.md` requires that file to change in the same commit as any behaviour it describes (repo). One wrinkle the codebase reading surfaced and could not resolve: `AssistantContextDocument.render` writes a per-item `done/outstanding` status into the ask context document, while `PRIVACY.md` says the summary is built "without… completion state"; whether the server path actually ships that field is flagged for verification, not asserted (`Assistant/AssistantContextDocument.swift` lines 108-140 and 283-295; `docs/PRIVACY.md` around line 114, repo). Any agent integration that adds egress should settle that discrepancy first, since it will be re-examined the moment the privacy copy is rewritten.

## Six architectures, and the wall each one hits

The candidate designs sort cleanly once the facts above are in hand. The table gives the verdict; the prose gives the reasons and the confidence behind each.

| Architecture | Can the agent act on Canvas? | Hard blocker | Platforms it serves | Verdict |
|---|---|---|---|---|
| A. Cookie export to agent or cloud browser | Yes, for about a day | Bearer credential leaves the phone; no renewal; Duo trust not portable; privacy posture and 5.1.1(v) spirit | Any that imports cookies (none documented except Browser Use, from local Chrome) | Reject |
| B. Phone as authenticated proxy | In theory | iOS suspension, 30 s silent-push budget, two-to-three pushes per hour, no delivery to force-quit apps, background crash | Cloud VMs via a relay | Reject for unattended use |
| C. Mac companion with local MCP server | Yes, inside the Mac app's own session | Mac must do its own PennKey plus Duo; Instructure's "unapproved MCP" clause; Mac sandbox unresearched | Claude Desktop, Claude Code, ChatGPT desktop (dev mode); not phone apps or cloud VMs | Realistic, the only defensible "act" design |
| D. Agent in the student's own Chrome profile | Yes, as the student | Desktop only; prompt injection; nothing for Smooth to build | Claude in Chrome, ChatGPT extension/desktop | Realistic today with zero Smooth changes |
| E. App Intents / Apple Intelligence on-device | Read yes; act only via Smooth's own WebView | No iOS surface drives a web form; ~20-30 s intent window; no Siri bridge to ChatGPT/Claude | Siri, Shortcuts, Spotlight, Apple Intelligence | Realistic for read and "open in Smooth" |
| F. Remote MCP backed by Smooth's backend | Read only | Work list would have to leave the phone (principle 2); server acting on Canvas breaks principle 1 | Claude any plan, ChatGPT dev mode then directory, probably dots/Duet | Realistic for read with a privacy-copy change; never for act |

**A, cookie export,** is mechanically trivial, which is what makes it tempting. `WKHTTPCookieStore` exposes `getAllCookies` and `setCookie` on iOS 11 and later, so Smooth could read its jar and hand the Canvas cookie to a cloud browser profile ([WKHTTPCookieStore](https://developer.apple.com/documentation/webkit/wkhttpcookiestore), primary). Everything after that step fails. The cookie's server lifetime defaults to a day and Smooth does not know the real value; the exported copy carries no IdP session, no Duo trust and no password, so it cannot be renewed; Browser Use's own guidance to refresh profiles weekly shows the phone would be re-pushing a fresh bearer credential to a third party on every renewal ([Browser Use](https://docs.browser-use.com/cloud/guides/profile-sync.md), search summary); and an export of "the saved set" from the live build might well contain a dead `canvas_session` beside live analytics cookies, the exact state read off Marco's phone on 2026-10-08 (`CLAUDE.md`, repo). Apple's guideline 5.1.1(v) says an app "may not store credentials or tokens to social networks off of the device and may only use such credentials or tokens to directly connect to the social network from the app itself while the app is in use"; it is written for social networks and its literal reach to an LMS is unclear, but it is the nearest statement of Apple's stance and a reviewer could read Canvas into its spirit ([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), primary, page dated 2026-10-16). It also contradicts Smooth's privacy copy and PROTOCOL principle 1 outright, and Penn's position that "you remain responsible for anything done with your PennKey" makes the student the one holding the bag when the cookie is misused ([PennKey Support](https://pennkeysupport.upenn.edu/node/16), search summary).

**B, phone as proxy,** founders on Apple's background model rather than on policy. Apple's text is unambiguous: a background push gives the app "up to 30 seconds to complete its work", "If you send background pushes more frequently than three times per hour, the system imposes rate limitations", delivery is "not guaranteed" and "low priority", and "If something force quits or kills the app, the system discards the held notification" ([Choosing background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app), primary; [Pushing background updates](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app), primary). `BGAppRefreshTask` is likewise 30 seconds at a time of the system's choosing; `BGContinuedProcessingTask` (iOS 26) needs a foreground user tap to start and shows a Live Activity ([BGContinuedProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask), primary). PushKit is call-only, and guideline 2.5.4 limits background services to their "intended purposes" ([PushKit](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit), primary; [Guidelines](https://developer.apple.com/app-store/review/guidelines/), primary). A phone LAN listener is no better: Apple's DTS says "The system will defunct stuff immediately on suspending your app" and advises stopping listeners when eligible for suspension ([forums 840808](https://developer.apple.com/forums/thread/840808), primary forum post by Apple staff). Add Smooth's own state, every background wake has crashed since 2026-08-24 with `_dispatch_assert_queue_fail` on the `BGTaskScheduler` queue (`CLAUDE.md`, repo), and the agent gets a proxy that answers only when the student happens to have Smooth open, which is when the student could have done the task themselves. The only iOS precedent found, Pushcut's Automation Server, "only processes requests while the Pushcut app is in the foreground" and recommends a dedicated always-on device ([Pushcut](https://pushcut.io/help/automation_server), search summary); the Android phone-proxy services have no iPhone equivalent, plausibly for exactly this reason.

**C, Mac companion,** is where the student's session can be used without leaving the student's own device. Smooth already builds for macOS from the same source with a menu-bar extra that keeps the sync loop alive (`LHFScenes.swift`, repo); `WKWebsiteDataStore.default()` "stores data persistently to disk", so a Canvas login on the Mac survives between launches ([WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore), primary); and a Mac is not suspended the way iOS suspends. The MCP spec defines stdio and Streamable HTTP transports, says clients "SHOULD support stdio whenever possible", and requires local HTTP servers to bind to localhost and validate `Origin` ([MCP transports, 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports), primary); Claude Desktop reads local servers from `claude_desktop_config.json` and Xcode 26.3 itself ships an MCP bridge, so the pattern is mainstream ([InfoQ](https://infoq.com/news/2026/02/xcode-26-3-agentic-coding), search summary). The design that follows is a tiny stdio shim that talks to the running Smooth Mac app over a local socket, exposing a handful of typed tools: list pending work, get one assignment, and submit a specific local file or text to a specific assignment, each executed by Smooth's own code with the cookie never leaving the process and a confirmation dialog in Smooth before any POST. The costs are real: the Mac must do its own PennKey and Duo sign-in because the iPhone's cookies are ThisDeviceOnly and cannot be made synchronizable (Apple, primary, above), the renewer logic must run on the Mac, the Mac has no field evidence for the universal-link guard or for Duo trust persistence, and the Mac sandbox and notarization requirements for a bundled helper were not researched. It serves desktop agents only; a dots or Duet VM cannot reach a localhost server.

**D, the student's own Chrome,** needs no Smooth code at all and is live today. The student signs in to Canvas in Chrome once, with PennKey and Duo, and Duo's 30-day trust lives in that Chrome; Claude in Chrome then acts in that signed-in profile with its per-site permission model and pauses on consequential actions ([Claude Help](https://support.anthropic.com/en/articles/12012173-getting-started-with-claude-for-chrome), primary). Smooth's contribution shrinks to telling the agent *what* to do, which is architecture E or F. The cost is the prompt-injection surface: Anthropic's pilot measured attack success at 23.6% without mitigations and 11.2% with them in August 2025, a figure Simon Willison called unacceptable, and the safety page's current claim of under 0.08% in internal testing is Anthropic's own number ([Anthropic: Claude for Chrome](https://www.anthropic.com/news/claude-for-chrome), search summary; [Willison](https://simonwillison.net/2025/Aug/26/piloting-claude-for-chrome/), search summary; [Claude Help: safety](https://support.claude.com/en/articles/12902428), primary). A Canvas page is full of instructor- and classmate-authored text, which is precisely the injection vector.

**E, App Intents,** is the native iOS answer and it stops at the browser's edge. WWDC26 session 240 says Siri in the 27 releases can access an app's entities, act through its intents and understand on-screen context, with App Intents as "the foundation" and `IndexedEntity` for semantic search ([Apple WWDC26 240](https://developer.apple.com/videos/play/wwdc2026/240/), primary). Apple documents that "Most app intents run quietly in the background" and can bring the app forward, with no published time limit; developers measure roughly 20-30 seconds ([Configuring the runtime behavior](https://developer.apple.com/documentation/appintents/configuring-the-runtime-behavior-of-your-app-intents), primary; [forums 716561](https://developer.apple.com/forums/thread/716561), community). Smooth's cookies are already `AfterFirstUnlock`, which Apple recommends "for items that need to be accessed by background applications", so a background intent can read the ledger and even do one short cookie-authenticated GET, but an SSO re-login does not fit the window (Apple, primary, above). An `AssignmentEntity` with title, course, due date, submission state and Canvas URL, plus intents for "what's due" and "open this assignment in Smooth", fits every privacy promise because nothing leaves the device; the on-device `OnDeviceAssistantResponder` already computes the exact answers (repo). What does not exist on iOS is any surface by which Siri, Shortcuts or Apple Intelligence fills and submits a web form inside another app's WebView, and nothing found says Apple Intelligence will invoke third-party intents on behalf of a ChatGPT or Claude agent; the minimum OS and region requirements for the WWDC26 features were also not confirmed.

**F, remote MCP on Smooth's backend,** is the design that reaches every agent platform and the one that collides hardest with Smooth's charter. The Supabase project is the natural OAuth authorization server for RFC 9728 metadata and audience-bound tokens, and a public HTTPS endpoint would work in Claude on any plan and in ChatGPT via developer mode and then the plugin directory (Anthropic and OpenAI docs, primary, above). But the server holds no per-student work state and is promised never to receive it, so a "list my assignments" tool means uploading the work list and submission state, a privacy change that touches `PROTOCOL.md`, `docs/PRIVACY.md` and the App Store review notes in one commit and that Apple's 5.1.2(i) frames as sharing personal data "with third-party AI" requiring disclosure and explicit permission ([Guidelines](https://developer.apple.com/app-store/review/guidelines/), primary). A server tool that *acts* on Canvas is simply out: the server would have to hold the cookie and "talk to Canvas", the two things principle 1 forbids, and Instructure's API policy independently bars using the APIs "on behalf of any third-party" and names "model context protocol servers or other technologies not approved by Instructure" as restricted connection technologies ([Instructure API Policy](https://www.instructure.com/policies/canvas-api-policy), primary). The honest version of F is read-only, with an explicit per-install opt-in, a one-way push of a minimal work list from the phone, and a documented deletion path; the ambitious version is a relay to the phone, which inherits every failure of B.

## A borrowed session is a bearer credential nobody can scope

The threat model is the same whichever box in the table one picks, because Canvas offers no scoped delegation at Penn. An access token could be limited to developer-key scopes and revoked in Canvas settings; a cookie cannot be scoped at all, it is the student's full web identity, and Penn has made the token unavailable. So any credential that reaches an agent is all-or-nothing, and the OWASP agentic top ten's ASI03, identity and privilege abuse, applies in its strongest form ([Descope summary of OWASP](https://www.descope.com/blog/post/owasp-agentic-top-10-identity), search summary; primary OWASP document not fetched). The vendors that have thought about this longest converge on one pattern: keep the secret out of the model. 1Password's Agentic Autofill lets the agent request a credential, has the human approve in 1Password, fills the password or one-time code, and removes it after login so "the agent never receives the value" ([1Password](https://1password.com/blog/closing-the-credential-risk-gap-for-browser-use-ai-agents), search summary); Arcade issues just-in-time authorization so the agent never sees the raw token; the MCP spec forbids token passthrough for the same reason ([MCP authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization), primary). Applied to Smooth, that pattern says the credential stays inside Smooth's process (phone or Mac), the agent receives only a short-lived, audience-bound token that authorizes it to *Smooth*, and Smooth translates a few allowlisted verbs into Canvas calls after an on-device confirmation. No source describes this for Canvas; it is a design inference from 1Password and Arcade.

Three Smooth-specific hazards sharpen it. First, Duo's `browsertrust` cookie is as sensitive as the session cookie: whoever holds it skips the second factor for a month, so it must never be exported and never be included in any "cookie set" an agent sees; the renewer's harvest filter keeps every cookie whose domain contains "canvas", not Duo's, but a naive `getAllCookies` export would sweep it up (`CanvasSessionRenewer.swift`; `CLAUDE.md`, repo). Second, server-side logout is global: because Canvas invalidates by `last_logged_out`, a student who signs out of Canvas in Safari would kill the agent's session too, which is a safety feature and an availability bug at once (inference from [authentication_methods.rb](https://raw.githubusercontent.com/instructure/canvas-lms/master/lib/authentication_methods.rb), primary). Third, free-form control is a review risk in its own right: guideline 2.5.2 forbids downloading or executing code "which introduces or changes features or functionality of the app", so an agent sending arbitrary JavaScript to run in Smooth's WebView is out, while fixed, typed actions are not ([Guidelines](https://developer.apple.com/app-store/review/guidelines/), primary). Prompt injection is the attack that makes all of this matter: a Canvas discussion post or a syllabus PDF saying "submit the attached file to every assignment" is exactly the kind of content an agent in architecture D reads with full privileges, and the measured residual success rates above are the reason every platform gates irreversible actions behind a human.

Apple review adds two lines that are easy to cross by accident. 5.1.2(i) requires clear disclosure and explicit permission before personal data is shared "with third parties, including with third-party AI"; 5.2.2 requires that an app displaying or acting on content from a third-party service be "specifically permitted to do so under the service's terms of use", with authorization provided on request ([Guidelines](https://developer.apple.com/app-store/review/guidelines/), primary). The second is the quiet one: Smooth already reads Canvas as the student, and an "act" feature invites a reviewer to ask for Instructure's permission, which the API policy's third-party and MCP clauses suggest would not be forthcoming without a developer key. The guideline text in the notes passed through a summarising fetch tool, so wording should be re-checked against the live page before it is quoted in a submission.

## Instructure, Penn and the vendors all have a line this crosses

The policy exposure is layered and mostly points the same way. Instructure's API policy, effective 2024-12-15, requires applications to disclose at registration the actions they take on behalf of users, forbids using the APIs "on behalf of any third-party", restricts unapproved connection technologies including MCP servers, requires disclosure of generative-AI use, prohibits use that violates a customer's academic-integrity policy where the user knows or should know, and reserves the right to revoke tokens for excess load ([Instructure API Policy](https://www.instructure.com/policies/canvas-api-policy), primary). Whether a cookie-authenticated client is an "application" under that policy is an inference, but the language is written for applications regardless of auth mechanism, and the GAI-disclosure clause bites any design that lets a model see or touch coursework. Canvas's end-user Terms of Use were not retrieved.

Penn's position on the credential is clear even where the documents could not be fetched. The Almanac states that sharing a PennKey password is a policy violation ([Almanac](https://almanac.upenn.edu/articles/sharing-your-pennkey-password-is-not-smart), primary), and PennKey support says the student remains responsible for anything done with it ([PennKey Support](https://pennkeysupport.upenn.edu/node/16), search summary). Smooth's `PRIVACY.md` already argues that storing the password in the phone Keychain and sending it only to Penn's login page is "comparable to a password manager's autofill"; an external agent exercising the resulting session is a different act, closer to lending the account, and the student is the one Penn would hold accountable. Penn's Acceptable Use Policy text itself 404'd and should be read before any launch copy mentions it.

Academic integrity is where "do it, and turn it in" splits into two very different asks. Penn's Code is framed around "unauthorized assistance" with instructors defining it per course, and Penn teaching guidance says submitting work containing AI-generated content "will be considered a violation of Penn's Code of Academic Integrity" unless authorized ([CETLI](https://cetli.upenn.edu/resources/syllabus/academic-integrity-syllabus/), search summary; the Code's own text was not retrieved). Both vendors' usage policies reach the same place: Anthropic's AUP bars "Plagiarize or submit AI-assisted work without proper permission or attribution" and says agentic use cases must comply ([Anthropic AUP](https://www.anthropic.com/legal/aup), primary), and OpenAI's policies prohibit use for "academic dishonesty, deceit, fraud, scams, spam, or impersonation", with a revision effective 2026-11-20 whose wording was not checked ([OpenAI usage policies](https://openai.com/policies/usage-policies/), search summary, page 403). No agent-specific refusal rule about coursework was found; what exists is confirmation prompts on consequential actions on every platform (Claude connectors ask before tool calls and Anthropic recommends disabling write tools in Research mode; OpenAI tells servers to require confirmation for consequential writes), and these would plausibly fire on "turn it in" ([Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), primary; [OpenAI: build an MCP server](https://developers.openai.com/plugins/build/mcp-server), primary). The distinction worth building the product around is between an agent that *produces* the work, which is exposed on every axis above, and an agent that *delivers* work the student authored, which is a narrower question none of these sources answers and which instructors still decide course by course. Marketing anything as "your agent does your homework" is the one move that converts a technical project into a policy problem with Penn, Instructure, Apple and both model vendors simultaneously.

## What is realistic, ranked, and what Smooth would have to change

Ranked by how much of the student's wish they deliver per unit of risk and work, the options come out as follows. Every ranking judgment here is an inference from the evidence above, not a sourced claim.

**1. Expose the work list on-device through App Intents, and ship nothing else first.** This answers "see my pending assignment on Smooth" for Siri, Shortcuts, Spotlight and Apple Intelligence, costs no egress, needs no privacy-copy change, and lands the `AssignmentEntity` and "open in Smooth" intent that every later option reuses. Changes: an App Intents target or in-app intents reading the SwiftData ledger; `IndexedEntity` conformance; an intent that opens the assignment's Canvas URL inside Smooth's signed-in WKWebView. Blockers: none on review; the WWDC26 Siri features' minimum OS and region are unconfirmed, so build on the iOS 18-era Shortcuts/Spotlight baseline and let Siri integration arrive with the OS. It does not get an agent into Canvas, and it should not claim to.

**2. Tell the student to use Claude in Chrome or the ChatGPT extension in their own signed-in Chrome, and let Smooth supply the list.** This is the only path that works *today* for "open the Canvas link, do it, and turn it in", because the session, the Duo trust and the human-approval model all already exist in the student's Chrome. Smooth's change is a way to hand the list across, which is option 1 on a Mac (Shortcuts) or the read-only connector in option 4. Smooth takes on no credential risk and no Instructure exposure; the student takes on prompt-injection risk the vendors already disclose.

**3. Build the Mac companion with a local, typed MCP server, if "act" must be a Smooth feature.** This is the only "act" design in which the credential never leaves the student's own device and every write is confirmed in Smooth's UI. Changes: run the Canvas login pane and renewer on macOS (own PennKey plus Duo, own persistent WebKit store); add Smooth's first Canvas write path, a CSRF-aware URLSession client for `POST .../submissions` and the three-step file upload, exercised against real Canvas for the first time since nothing in the repo ever has been; a stdio shim and local socket; a confirmation sheet before any POST; `PRIVACY.md` and review notes updated in the same commit. Blockers: Instructure's MCP and on-behalf-of clauses, which argue for a quiet, personal-use posture rather than a marketed feature; Mac sandbox and notarization for the helper, unresearched; desktop-only reach. It should be scoped to the five API-submittable types and refuse New Quizzes and LTI/Gradescope rows outright rather than fail half-way.

**4. Add a read-only remote MCP connector only if cloud agents (dots, Duet, Muse) matter, and only behind an explicit opt-in.** Changes: a per-install consent switch; a minimal work-list push (title, course, due, Canvas URL, submission boolean) from the phone to a new table keyed to the anonymous account; RFC 9728 metadata and audience-bound tokens on the Supabase side; a deletion path wired into the existing Canvas-disconnect cleanup; rewritten PROTOCOL principle 2, `PRIVACY.md` and App Store review notes in one commit; 5.1.2(i) disclosure in-app. Blockers: it reverses a published promise, and because Smooth's backend is Penn-only by course-id keying, so is this. It must never grow a write tool.

**5. Reject the phone-as-proxy relay.** iOS gives 30 seconds a few times an hour at best, nothing to a force-quit app, and Smooth's background path has never run without crashing. A proxy that works only while the student is looking at Smooth is not a proxy.

**6. Reject cookie export in every form, including "just for 24 hours".** It hands a third party an unscopable bearer credential, loses the renewal capability that only the WebKit store and password provide, risks sweeping up Duo's trust cookie, contradicts `PRIVACY.md` and PROTOCOL principle 1, reads against 5.1.1(v)'s spirit, and leaves the student answerable to Penn for whatever the agent does. The Canvas access-token path that would make a scoped version possible exists in the code and is blocked by Penn, not by Smooth; the day Penn issues a developer key or lifts the restriction, revisit from `FeatureFlags.canvasAccessTokens`.

Two prerequisites sit under all of these and are already on `ROADMAP.md`: land and compile the analytics-cookie fix now in the working tree, since any agent reading `canvasSubmitted` from a phone in that state is reading a stale poll with no banner to say so, and fix the background-refresh crash together with a foreground-only guard on the renewer, since every option above inherits whatever session freshness Smooth can actually maintain. Nothing in this research compiled or ran any code; by the project's own rule, the working-tree fix is not done.

## Conclusion

The question assumed that Smooth's persistent sign-in is a thing that could be lent out, and the code says it is not a thing at all but a process: a foreground WebView, a WebKit data store full of IdP and Duo cookies, a saved password, and a local 24-hour clock that decides when to run them. The Canvas cookie is the output of that process, good for roughly a day, and exporting it exports the least valuable part. That reframing moves the engineering question from "how do we share the session" to "where can the process itself run", and the only honest answers are the student's own Mac, either as a Chrome profile the agent already drives or as a Smooth companion that signs in on its own and executes typed verbs under confirmation.

It also exposes a structural mismatch between the agent products and the institution. dots, Duet and Muse are built around cloud VMs that treat login walls as a human-takeover moment, while Penn has removed the scoped token that would let a third party act without a login wall at all and binds second-factor trust to a single browser. Until Instructure or Penn issues a developer key to a student-facing app, every Canvas-acting agent at Penn is a browser that a human logged into, and Smooth's best contribution is to be the fastest, most trustworthy source of *what* needs doing, with "turn it in" left as a confirmed, student-initiated act on a device the student owns.
